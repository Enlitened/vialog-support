An injection schedule that survives daylight saving: identity is not an instant

Colin Sergay · 23 October 2026

Vialog is an iPhone journal for an injection routine someone already follows. The routine has a schedule, and each scheduled entry needs a name that lasts as long as the record does. This is why that name is never a point in time.

The obvious key, and where it breaks

A schedule that says "daily at 08:00" produces a stream of expected entries. Each one can be recorded, marked as skipped, snoozed from a notification, or left alone and shown as not logged. All of those need to point at the same entry, and the tempting key is the moment it is due: a Date, which is unique, sortable and already there.

I live in Australia, where the clocks move twice a year, and the instant fails on exactly those two nights.

  • Spring forward. In Sydney on 4 October 2026 the clock goes from 02:00 straight to 03:00. An entry at 02:30 has no instant at all. Whatever Date you get is an artefact of whichever API you asked, and two code paths that ask differently give the same entry two keys.
  • Fall back. On 5 April 2026, 02:30 happens twice, an hour apart. Now two instants could claim one entry, and a generator that is careless about it produces two.
  • Travel, and every other day. An 08:00 entry in New York is 13:00 UTC in January and 12:00 UTC after the March change. The instant is derived from a zone's rules, and the rules are not the identity.

If the stored record says "the entry at 2026-03-09T12:00Z", that string is only correct for as long as every part of the app computes the instant the same way, from the same zone, under the same tz database. That is a lot to promise for a record someone might export years later.

What the key is instead

An entry is named by three things: the schedule version that produced it, the local calendar day it belongs to, and the slot (one time of day in that version, with its own UUID). The instant is derived from those, never the other way round.

/// Version, nominal local day and slot — never the instant. The instant is derived, and the
/// two days a year it moves by an hour are exactly the days the identity must not.
nonisolated struct OccurrenceKey: Hashable, Sendable, Codable {
    let scheduleVersionID: UUID
    let localDay: LocalDate
    let slotID: UUID

    /// The stored form: `<version>|<yyyy-MM-dd>|<slot>`.
    var token: String {
        "\(scheduleVersionID.uuidString)|\(localDay.token)|\(slotID.uuidString)"
    }
}

LocalDate is year, month and day with no zone, and LocalTime is hour and minute. The slot has an id separate from its time so that moving a slot from 08:00 to 08:30 keeps it the same slot, while adding a second slot at 08:00 makes a different one. Each schedule version carries its own IANA zone, chosen in the editor's "Schedule zone" row and defaulting to the device's zone when the routine is made. The generator reads every day and slot in that zone; nothing in it reads the clock or the device's zone.

That is the answer to travel. Changing the device's zone does not change which entries exist or when they are due. If someone wants the plan read in the new zone, that is a schedule change, and a schedule change is a new version, which I come to below.

The policy, stated once

Deriving the instant still has to answer the two awkward nights. Vialog answers them in one function, OccurrenceGenerator.instant(for:on:in:), and nowhere else:

  • A wall-clock time that does not exist moves forward by the length of the gap and keeps its minutes: 02:30 becomes 03:30.
  • A wall-clock time that exists twice uses the first.
guard let start = day.startOfDay(in: calendar) else { return nil }
let components = DateComponents(hour: time.hour, minute: time.minute, second: 0)
// `after:` is exclusive, so search from just before the day starts.
guard let first = calendar.nextDate(
    after: start.addingTimeInterval(-1), matching: components,
    matchingPolicy: .nextTimePreservingSmallerComponents,
    repeatedTimePolicy: .first, direction: .forward
) else { return nil }

// Was the time moved? Compare what the clock reads at the instant with what was asked.
let resolved = LocalTime(from: first, calendar: calendar)
if resolved != time || LocalDate(first, calendar: calendar) != day {
    return (first, .movedForward(resolvedTime: resolved))
}

The detail that matters is the matching policy. .nextTimePreservingSmallerComponents keeps the minutes when it has to move an hour that is not there. The convenient date(bySettingHour:minute:second:of:) collapses a nonexistent 02:30 to 03:00, so the code's own comment says it is deliberately not used. Thirty minutes may not sound like much, but it means two ways of computing the same entry disagree, and the disagreement only shows up one night a year.

The repeated hour is detected separately. A second search with repeatedTimePolicy: .last would find the same instant on every ordinary day, and this runs for every slot of every day a window covers, so the function first asks the zone for its next daylight-saving transition and makes the second search only when one falls within 26 hours of the day's start. When the two searches disagree, the entry is marked .firstOfRepeatedTime. Either way the adjustment is recorded on the Occurrence beside its due instant, not folded into its key.

Two smaller things follow from keying on the local day. The generator walks one local day before the requested window and one after it, because a slot's instant can land on a different UTC day from its nominal local day. And a planned quantity that changes over time is stored as steps keyed on the local day, so a step applies from the day it names whatever the clocks did to that day's instants.

A change is a new version

The first part of the key is the version, and that is what keeps history still. A SchedulePlan is immutable once it has started. Changing the schedule never edits it: ScheduleEditor.change closes the version in force at the "changes from" instant (its effectiveUntil, which is exclusive, moves there) and adds a new, open-ended version that starts at the same instant. An entry exactly at the boundary belongs to the new version. Every entry and record the old version produced keeps pointing at it, so last month reads exactly as it did.

The boundary has one rule worth showing. A change may not start before an entry the user has already dealt with:

static func earliestEffectiveFrom(now: Date, resolvedDueInstants: [Date]) -> Date {
    guard let latest = resolvedDueInstants.filter({ $0 >= now }).max() else { return now }
    return latest.addingTimeInterval(1)
}

Vialog/Domain/ScheduleEditor.swift.

Without it, recording this evening's entry early and then changing the schedule from this afternoon would leave that record under a version that no longer covers its instant, and the new version would offer the same slot again as not logged. Pushing the boundary one second past the latest resolved entry keeps one entry, one record. A version that has not started yet can be withdrawn instead, and withdrawing it reopens the version that was closed for it.

Why that makes writes safe to repeat

Recording is idempotent on a commandID, a UUID fixed when the user taps, not on any timestamp. A tap on the Apple Watch keeps its id whether it reaches the phone as a live message or a queued transfer, so if both land it is recorded once. The store looks for the command first and returns the earlier outcome if it finds one. Two separate unscheduled injections recorded in the same second carry different command IDs, so they are two records, and that is correct.

For a scheduled entry, the store then re-derives the entry from the schedule as it stands now, from its key alone:

func recordAdministration(_ command: RecordAdministrationCommand) -> … {
    if let existing = administration(commandID: command.commandID) {
        return .success(RecordOutcome(administrationID: existing.id, /* … */ wasAlreadyApplied: true))
    }
    // … routine exists, is not archived, the time is not in the future …
    if case .occurrence(let key) = command.target {
        guard let current = currentOccurrence(for: key, routineID: routine.id) else { return .failure(.staleOccurrence) }
        guard resolution(for: key) == nil else { return .failure(.occurrenceAlreadyResolved) }
        occurrence = current
    }
    // … insert the record and its resolution, then one save …
}

Vialog/Persistence/VialogStore.swift, simplified where marked with ….

currentOccurrence goes to RoutineTimeline.occurrence(for:), which finds the version by its id and the slot by its id, checks the day is a real calendar day in the version's zone and inside the recurrence, resolves the wall-clock time with the same instant(for:on:in:), and checks the version is in force at that instant and no pause covers it. The key is either still produced, or it is not.

That is what makes an old notification harmless. A reminder's payload carries the key's token. If the schedule changed after the banner was delivered, that version no longer produces that day's entry, and "Record as skipped" from that banner is refused with .staleOccurrence, whose message reads "This entry belongs to a schedule that has since changed." Nothing is written against an entry that no longer exists, and nothing is guessed from the time on the banner.

The reminder planner relies on the same property in the other direction. Its window starts one day before now (ReminderPlanner.lookbackDays = 1), because a snooze is asked for after the banner fired, when the entry it names is already behind the clock. A window that began at now could never find it, and the snooze was dropped. A delivered banner comes down when its key is resolved or no longer produced, never merely because its due time has passed.

How the tests pin it down

The policy is tested as scheduling behaviour, with real zones and real 2026 transition dates, in VialogTests/OccurrenceTests.swift:

@Test func newYorkSpringForwardMovesANonexistentTimeForward() {
    // 2026-03-08 02:00 EST → 03:00 EDT. 02:30 does not exist.
    let plan = Fixture.dailyPlan(routineID: routineID, from: Fixture.utc(2026, 3, 1),
                                 times: [LocalTime(hour: 2, minute: 30)], zone: Fixture.newYork)
    let occurrences = OccurrenceGenerator.occurrences(for: plan, in: Fixture.utc(2026, 3, 8)..<Fixture.utc(2026, 3, 9))
    #expect(occurrences.count == 1)
    let occurrence = occurrences[0]
    #expect(occurrence.dueAt == Fixture.utc(2026, 3, 8, 7, 30))  // 03:30 EDT
    #expect(occurrence.daylightSavingAdjustment == .movedForward(resolvedTime: LocalTime(hour: 3, minute: 30)))
    #expect(occurrence.key.localDay == LocalDate(year: 2026, month: 3, day: 8))
}

VialogTests/OccurrenceTests.swift; one call rewrapped.

  • identityIsVersionDayAndSlotNotInstant generates 7–9 March in New York and checks the three keys exactly, while the due instants move from 13:00 to 12:00 UTC across the change, and that every key's token parses back to the same key.
  • newYorkFallBackUsesTheFirstOfARepeatedTime takes 01:30 on 1 November 2026 and expects one entry, at 05:30 UTC, the earlier of the two.
  • sydneyTransitionsFollowTheSamePolicy runs both Australian nights for a 02:30 slot: the repeated one in April, the skipped one in October, which lands at 03:30.
  • directLookupMatchesEveryGeneratedEntry runs a year of five slots in New York, Sydney, Cairo (whose clocks spring forward at midnight, so one day has no 00:00) and Lord Howe Island (whose transition is half an hour), and checks that looking up each generated key by itself returns the same entry, and that keys inside a pause, before the start or after the end, or naming an unknown slot, return nothing.
  • lookupRejectsANormalizedOrSkippedCalendarDay uses Pacific/Apia, which skipped 30 December 2011 entirely, and 31 February, so a key naming a day that never happened cannot be read as one.

On the store side, StoreTests has recordingTheSameCommandTwiceLandsOnce, aStaleOccurrenceCannotBeRecordedOrSkipped (a replaced plan's entry, a slot the version never had, and an archived routine), aChangeCannotCutOffAnOccurrenceRecordedEarly, and changingTomorrowLeavesLastMonthIdentical, which records an April entry, changes the schedule in May and checks that April's entries compare equal to what they were before. ReminderPlannerTests has aSnoozeForAnOccurrenceThatHasAlreadyFiredIsPlanned for the look-back.

What I would tell myself at the start

Store the thing the user chose (a day, a time of day, a zone, a version) and derive the thing the system needs (an instant), in one function, with the edge cases written down where the function is. Everything downstream got simpler once the key stopped depending on the clock: retries became lookups, an out-of-date banner became a refusal with a reason, and the two odd nights a year became tests rather than bug reports.
